## Customer model

The three personas below are concrete operating roles from the brief's Users and Top Workflows sections. Their weekly frequency is the brief's role model, not a claim that interviews or usage analytics were collected. The brief contains User Vision (the linked MCP's scope and read-only testing authorization) and no Codebase Intelligence section. This is a first print: prior research is `none`.

### Agency integration maintainer

**Today (without this CLI):** The maintainer lists businesses, then accounts and numbers, and consults Meta's app/business settings when a prerequisite fails. The official catalog separates owned accounts, customer-shared accounts and account models; names alone do not establish a relationship. The brief supports this traversal but does not establish which business Bobe wants selected.

**Weekly ritual:** Revisit an explicitly chosen client/business integration, establish the account and sender context, and review the captured configuration before preparing changes.

**Frustration:** Reconstructing the same scope across separate responses, especially when a partial page or a shared account makes a relationship unresolved.

### WhatsApp integration developer

**Today (without this CLI):** The developer reruns onboarding_status for a chosen business, app or number and inspects webhook subscription and publication results. The server can already perform these reads; a new CLI adds value only when it retains comparable evidence over time or detects contract drift.

**Weekly ritual:** Resume unfinished onboarding or webhook debugging, distinguish changed configuration from an unknown check, and verify that scripts still match the beta tool contract.

**Frustration:** A current-state response cannot show what changed since the previous capture, and the observed catalog already differs from the documentation.

### Template operations owner

**Today (without this CLI):** The owner lists templates in a chosen account and retrieves full details before preparing a change or send. The authenticated contract distinguishes template creation capabilities from the smaller set of components the MCP send tool can express.

**Weekly ritual:** Review approved template content, compare a chosen account's template with a selected counterpart, and assemble the real parameter values needed by a send.

**Frustration:** Account-scoped documents and component details require manual comparison; approval alone does not establish that the MCP tool can represent all required components.

Wrapper test and transcendence proof: A local cross-entity relationship view, not an alias for one discovery tool. Closest killed sibling: Universal readiness score. Buildability: `hand-code`; a small Cobra command can use shared snapshot/JSON-diff helpers, and the feature-specific code stays below 200 lines rather than duplicating infrastructure. Long-description check: every redirect names a surviving command with the exact final `ops` path. Data-source strategy: `// pp:data-source local`; reject `--data-source live` before access. Constraints: Require explicit chosen scope; never infer that Bobe selected one of the discovered businesses. Preserve separate owned/shared relations, capture time, incomplete pages and unknown links. Do not equate prerequisites_met with readiness.

**Captured asset changes — adversarial answers.** Weekly use: The integration developer compares the last captured state with the current capture when resuming weekly setup and webhook work; this follows the brief rather than measured usage. Wrapper test and transcendence proof: Temporal evidence from SQLite cannot be returned by a single current-state MCP call. Closest killed sibling: Onboarding-ready shortcut. Never overwrite unknown with todo. Ignore only capture-envelope bookkeeping; do not silently normalize away API content.

Wrapper test and transcendence proof: It combines two account-scoped documents into a review artifact; the API offers only individual template reads. Closest killed sibling: Template translator. Do not infer that a missing template is absent from an account whose capture was filtered or incomplete. A diff does not approve deployment or category choice.

**Template component checklist — adversarial answers.** Weekly use: The template owner runs it when preparing template sends and reviewing template changes in the named weekly ritual. Wrapper test and transcendence proof: Local contract history and compatibility-oriented output are absent from a single tools/list response. Closest killed sibling: Pretty catalog list. Buildability: `hand-code`; a small Cobra command can use shared snapshot/JSON-diff helpers, and the feature-specific code stays below 200 lines rather than duplicating infrastructure. Long-description check: every redirect names a surviving command with the exact final `ops` path. Data-source strategy: `// pp:data-source local`; reject `--data-source live` before access. Constraints: Classify removed tools and newly required inputs as potentially breaking; show other changed schema paths without pretending to prove compatibility for arbitrary JSON Schema. Treat description-only changes separately. Compare the same endpoint/protocol catalog; do not call unrelated APIs.

All five share bounded storage infrastructure rather than implementing five independent databases: captured MCP response envelopes plus explicit scope/time/completeness metadata. Every local command calls `hintIfUnsynced` / `hintIfStale` on the relevant resource before returning results, with hints on stderr. Reads use the drain-first SQLite pattern: scan into plain structs, check `rows.Err()`, close rows, then perform subsequent queries or joins. Capture writes must not call store Upsert helpers inside another open write transaction. Keep business data local; archived live proofs contain outcomes and counts only. Unsupported result shapes produce an explicit unknown/error and do not become fabricated normalized entities. These are read-only analytical commands; capture creation belongs to the already absorbed read/sync behavior and requires explicit scope.
